## Task Summary
User requested fixing architecture duplication between CLI and TUI for plugin listing. The core problem was that CLI and TUI had separate implementations for loading and filtering plugin data, causing inconsistent behavior especially for plugins enabled via local scope override (E:l).

## Work Done
- Created `PluginDataProvider` service as single source of truth for plugin data loading and filtering
- Refactored CLI to use `PluginDataProvider.get_filtered_plugins()`
- Refactored TUI (MarketplaceView) to use `PluginDataProvider.get_filtered_marketplaces()`
- Cleaned up redundant `MarketplaceLoader` direct usage from app.py and marketplace_view.py
- Added `get_plugin_source_dir()` method to PluginDataProvider for plugin preview functionality
- Fixed broken tests that needed `project_config_path` parameter
- Created comprehensive test suite for PluginDataProvider (13 tests)

## Design Decisions
- **Single PluginDataProvider class**: Rather than adding filtering to MarketplaceLoader, created new wrapper class because it provides cleaner API and allows future expansion without modifying existing services
- **Explicit paths required**: No cwd fallback in PluginDataProvider - caller must provide explicit paths. This follows user's requirement that cwd should only be used in entry point (__main__.py) as default for --directory
- **Composition over modification**: PluginDataProvider wraps existing PluginLoader and MarketplaceLoader rather than modifying them

## Challenges & Solutions
| Challenge | Solution |
|-----------|----------|
| CLI and TUI had different filtering logic | Created unified `get_filtered_plugins()` method |
| TUI needs marketplace tree structure while filtering | Added `get_filtered_marketplaces()` that filters plugins but preserves marketplace hierarchy |

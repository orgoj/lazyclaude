## Design Decisions

### View-Based vs Modal-Based Architecture
**Decision**: Keep view-based architecture, adapt upstream changes to fit
**Rationale**:
- Local branch has significant investment in view-based marketplace (MarketplaceView widget)
- Upstream temporarily reverted to modal-based approach
- Converting entire branch back to modal would lose functionality (plugin preview mode, full-screen tree view, etc.)
- View-based is more scalable for marketplace browser UX

### Dynamic Footer Actions
**Decision**: Adopt upstream's reactive footer system
**Rationale**:
- Upstream's conditional actions (can_refresh, can_edit, can_copy, etc.) provide better UX
- Automatic hiding/showing of keybindings based on state
- More maintainable than hardcoded footer strings
- Preserved local's `set_content()` wrapper for backward compatibility

### Import Strategy
**Decision**: Keep both `PluginLoader` and `AppFooter` imports in TYPE_CHECKING block
**Rationale**:
- Both needed for type hints in different methods
- Minimal overhead (TYPE_CHECKING is compile-time only)
- Avoids circular import issues

## Lessons Learned

### Technical Lessons:

**Merge Conflict Patterns:**
- Import conflicts: Usually need both imports when TYPE_CHECKING blocks diverge
- Method conflicts: Check if methods serve different purposes - may need to keep both
- Architecture conflicts: One approach must win - don't try to mix incompatible paradigms

**Textual Reactive Patterns:**
- Reactive attributes automatically trigger watch_*() methods when changed
- _update_content() pattern: Update widget after reactive state change
- has_class("visible") pattern: Check CSS class presence instead of boolean attribute

**View-Based vs Modal-Based:**
- View: Full-screen widgets with CSS visibility classes
- Modal: Overlay widgets with show()/hide() methods
- Not easily mixable - choose one architecture per feature

### Process Lessons:

**Before Merging:**
1. Check architectural compatibility (view vs modal is big difference)
2. Run `git diff --stat` to see scope of changes
3. Read key upstream commits to understand direction
4. **NEVER abort merge without asking** - user may want to proceed

**When Resolving Conflicts:**
1. Understand WHY files conflict (not just HOW)
2. Check if conflicting code serves different purposes
3. Test early with quality gates
4. Keep architectural consistency

**Post-Merge Verification:**
1. Always run quality gates BEFORE committing
2. Test app startup (5-second timeout is sufficient)
3. Check for missing attributes/methods with mypy
4. Run full test suite
